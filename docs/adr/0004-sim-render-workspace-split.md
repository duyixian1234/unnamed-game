# Simulation/render split: a `game-core` + `app` Cargo workspace

The project is split into a two-crate workspace: `game-core` holds all simulation logic (state machine, waves, combat, economy, enemies, player, AI, RNG, intent layer) and depends only on minimal Bevy features (ecs, app, state, math, transform, time) — no render, window, or audio. The `app` crate is the binary: `DefaultPlugins`, sprites, audio, and UI, which read core state (via components/resources) and attach visuals to it; `Transform` lives in core, `Sprite`/UI do not. This was chosen over a single crate with feature-gated rendering because feature gates still pull full Bevy into test builds and are easy to leak; the split makes headless integration tests of the full game flow (fixed-timestep, single-threaded `App::update()`) physically possible. Consequence: trunk points at `app`, and any new gameplay code must land in `game-core` without render dependencies. Reversing this later means untangling every module, so it is recorded now.
